# Правила распределения ФУЛ (справочник)

Все решения принимает скрипт `scripts/distribute.py`. Этот справочник —
читаемое описание тех же правил для модели и для согласования с заказчиком.

## Входные файлы

Скрипт находит колонки по заголовкам (с учётом регистра, пробелов,
кавычек и подстрок), поэтому допустимы: другой порядок колонок, лишние
колонки, иное название листа, строка заголовков не на первой строке.
Формат — .xlsx.

### 1. Выгрузка ФУЛ из 1С (по строке на ФУЛ)

Дата, Cutoff date, Номер, Статус, Комментарий, Способ доставки,
Бизнес единица (бренд), Логист, Контрагент (поставщик), Страна.

Номер заказа извлекается из Комментария вида «Номер:S0001234 от
ДД.ММ.ГГГГ» (регулярное выражение по шаблону S + цифры).

### 2. Реестр Cloud (история заказов)

12 колонок: Заказ, Поставщик, Бренд, Логист, Статус, Дата подтверждения,
Cut-off, Дата получения УЛ, Страна отправления, Способ доставки,
Документы получены, Комментарий. Значения колонки «Логист» могут быть
короткими («Жуков», «Иванов И.И.») — они сопоставляются с ФИО из 1С
по фамилии и инициалам. Неверные инициалы не совпадают; если одна фамилия
подходит нескольким сотрудникам, имя считается неоднозначным и в истории
и загрузке не учитывается.

### 3. Сотрудники из 1С

Наименование (ФИО), Текущее состояние, Должность, Код (таб. №).

## Правила

1. **Новый vs повторный.** Если номер заказа из ФУЛ уже есть в колонке
   «Заказ» Cloud — это повторная отправка: новая строка не создаётся, в
   «Повторные отправки» попадает комментарий «Повторная отправка ФУЛа,
   [дата ФУЛ]». Если тот же номер заказа встречается дважды внутри одной
   пачки ФУЛ — второй является дублем: строка не создаётся, событие
   фиксируется в «Повторных отправках» и «Журнале решений».

2. **Группа.**
   - air → Авиаперевозки;
   - не air + страна отправления Китай, включая Гонконг и Макао → ВЭД;
   - не air + страна не Китай → Мультимодальные перевозки.
   Если нет способа доставки или (для не-air) страны — группа
   «не определено», заказ уходит в «Требует внимания», логист не
   назначается.

3. **Кандидаты.** В группе участвуют только сотрудники со статусом
   «Работает» и должностью «специалист …» соответствующего направления.
   Ассистенты и руководители групп заказы не распределяют, сотрудники
   в отпуске и уволенные исключаются.

4. **Выбор логиста.**
   - Считается история Cloud по поставщику: сколько заказов у каждого
     логиста (сопоставление коротких имён с ФИО). Назначается логист
     с наибольшим числом заказов, если он доступен.
   - Если лидер истории в отпуске или уволен — берётся следующий по
     истории доступный; если доступных по истории нет — наименее
     загруженный в группе.
   - Загрузка = число заказов со статусом «в работе» в Cloud плюс уже
     назначенные заказы из текущей пачки. При равенстве — по алфавиту
     ФИО (детерминированно).
   - Новый поставщик (нет истории) → наименее загруженный в группе.

5. **Один поставщик — один логист.** Все новые ФУЛ одного поставщика
   внутри пачки получают одного логиста (регистр, кавычки и пробелы в
   названии поставщика игнорируются). Если ФУЛ одного поставщика попали
   в разные группы, правило применяется внутри каждой группы отдельно.

6. **Нет доступных в группе.** Заказ остаётся без логиста (поле
   «не определено») и уходит в «Требует внимания». В другую группу заказ
   НЕ передаётся.

7. **Возможные пропуски.** ФУЛ с датой раньше последней записи Cloud
   (по «Дате получения УЛ»), заказ которого отсутствует в реестре, —
   попадает на лист «Возможные пропуски». Строка для него всё равно
   создаётся (см. допущение 6).

8. **Недостающие данные.** Везде, где данных нет, выводится строго
   «не определено» — никаких правдоподобных подстановок. Строка Cloud
   при этом создаётся, чтобы человек мог заполнить пробелы, и заказ
   дублируется на листе «Требует внимания» с указанием проблемы.

## Форма результата

`result.xlsx`, листы: «Новые строки Cloud» (ровно 12 колонок реестра,
в его порядке), «Повторные отправки», «Возможные пропуски»,
«Требует внимания», «Журнал решений» (основание каждого решения).

Новая строка Cloud: Заказ — из ФУЛ («не определено», если нет); Поставщик,
Бренд — из ФУЛ; Логист — назначенный или «не определено»; Статус —
«в работе»; Дата подтверждения и Документы получены — «не определено»
(заполняет человек при подтверждении); Cut-off — из ФУЛ; Дата получения
УЛ — дата ФУЛ; Страна отправления, Способ доставки — из ФУЛ («не
определено», если пусто); Комментарий — пустой.

## Принятые допущения (до ответов заказчика)

1. Дубль внутри пачки обрабатывается как повторная отправка: строка не
   создаётся, в комментарий дописывается «Повторная отправка ФУЛа, [дата]».
2. «Чаще всех работает с поставщиком» считается по всем строкам Cloud
   с этим поставщиком независимо от статуса.
3. «Наименее загруженный» считается по статусу «в работе»; заказы
   «confirm» в загрузке не участвуют.
4. Если ФУЛ одного поставщика в пачке имеют разные группы, правило
   «один поставщик — один логист» применяется внутри каждой группы.
5. «Возможные пропуски» не блокируют создание строки: сотрудник решает,
   вносить ли заказ, по данным листа.
6. Дата в комментарии повторной отправки — дата ФУЛ в формате ДД.ММ.ГГГГ.
7. Гонконг и Макао приравнены к Китаю при выборе группы ВЭД.
8. Сотрудник со статусом «Работает» доступен сразу; статусы с «отпуск»
   и «увол» — недоступны. Другие статусы (больничный и т.п.) трактуются
   как недоступные до уточнения.
